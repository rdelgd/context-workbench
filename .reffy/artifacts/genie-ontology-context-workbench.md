# A workbench for the context Genie relies on

Response to [seed.md](../../seed.md).

I’d make the workbench’s primary action **review a change in business meaning**. If someone proposes counting a vehicle sale on delivery instead of contract signing, the workbench should show which measures and Genie targets depend on that decision, which examples become misleading, and which benchmark answers should move. That review is the feature I’d borrow from Genie Workbench’s blueprint and evaluation workflow and apply to a business definition shared across consumers. [Genie Workbench semantic blueprint](https://databricks-solutions.github.io/databricks-genie-workbench/docs/features/semantic-model/)

## Where the workbench has authority

Databricks describes Genie Ontology as combining modeled knowledge that people govern through Unity Catalog with learned knowledge Genie extracts from assets and usage. I’d make the workbench authoritative for **which business definitions the team has approved, which governed assets implement them, and what evidence supports a given release**. An existing metric view can remain the executable authority for a calculation. The workbench can record the version reviewed and detect when the deployed definition drifts, without maintaining a second copy of the formula. [Genie Ontology](https://docs.databricks.com/gcp/en/genie/genie-ontology/)

A definition would have a stable identity, a business owner, and a scope. Bindings would identify the governed assets that implement or explain it. One binding might point to a Unity Catalog metric view, another to a Page that explains when to use the metric, and another to the knowledge store or examples of a curated Genie Agent. The first consumer can be a curated Agent because its configuration is inspectable and its answers can be benchmarked. A test of that Agent establishes evidence for that surface. Whether the same definition is selected through Genie Ontology is a separate behavior to test where that surface is in scope. [Genie Ontology](https://docs.databricks.com/gcp/en/genie/genie-ontology/), [Genie Agent concepts](https://docs.databricks.com/aws/en/genie-agents/concepts)

## A history of approved definitions

The Nuveris meaning-ledger note suggests keeping an append-only history of business definition decisions. Each accepted version would record the definition’s scope, when it takes effect, who approved it, why, and which policy authorized that person to approve it. A later decision would supersede the earlier one, so a reviewer could still reconstruct the meaning used for a past report or answer. Two business units could each approve a valid definition of the same term. If their owners agree that the definitions are equivalent or can be converted, record that relationship explicitly. Source is `.reffy/artifacts/lasm-meaning-ledger-on-databricks.md` in project `nuveris`, workspace `nuveris-v1`.

For the pilot, the decision history would link each approved definition to the exact versions of the governed assets that implement or explain it. Keep the calculation in the existing metric view and use those links to check whether the deployed assets still match what was reviewed. Generating metric views or Genie context from the history is an option to revisit if this pilot exposes gaps in asset versioning or release review.

## Sales pace is a useful first experiment

Use one dealership sales-pace definition and one evaluation Agent. Agree first on which events count, which local date controls month attribution, how to count elapsed selling days, and how to handle a group of stores with different calendars. Those are decisions for the business owner. A concrete test could put a contract on April 30 and delivery on May 1, with a store closure in the first week of May. A correct answer would have to choose both the approved attribution date and the approved denominator. The case should include rows whose results differ under the competing interpretations.

Compare the current and candidate context against the same data snapshot, effective date, and evaluation identity. Include a direct question, held-out rephrasings, a boundary case, and a question where the approved behavior is to ask for clarification. For numeric cases, compare with an independently reviewed expected result and inspect the generated SQL for date, scope, and grain. Keep evaluation questions and reference answers out of the material provided to Genie as tuning examples. Record the context version and target configuration with the results so a regression can be traced to the release that was tested. [Test and monitor a Genie Agent](https://docs.databricks.com/gcp/en/genie-agents/monitor)

I’d review two diffs together. A **definition diff** shows what the business agreed to change and which expected answers therefore should change. A **delivery diff** shows what Genie was given and which answers improved under the same expectations. A benchmark win can justify clearer instructions or a better mapping. Changing the expected meaning requires a decision from the owner. Skills can codify how to run this review, while the decision and evidence travel with the definition.

For a switch from contract signing to delivery, record the expected answer for the April 30 contract and May 1 delivery under each approved version before running the benchmark. Link the result to the definition version, Agent configuration, and evaluation identity. If two dealerships legitimately use different attribution rules, add a question spanning both and test whether Genie surfaces the difference or asks for clarification when there is no approved combined definition. The benchmark records how Genie behaved under those conditions. The business owner decides which definition and cross-store comparisons to approve.

The first experiment succeeds if a reviewer can trace a wrong answer to a specific definition, asset mapping, or delivery problem, then verify a correction on held-out questions. The open question worth testing first is how much of the existing meaning already lives in governed Databricks assets and can be referenced directly. That determines how much context the workbench needs to author itself.
